Are We Fast Yet?

Ractors, Fibers, and how far can we stretch it.

ruby 4.1.0dev master 9b8b0ae443go1.25.5Ryzen 7 9800X3D, 8 cores, 16 threads3 October 2026

I built the same small API gateway twice, once in Ruby on master and once in Go, and pushed both with wrk on the same four cores. The first version of this page was too kind to Ruby: almost all of its time went into C, sockets and the kernel. This version makes Ruby do the work. It parses HTTP into objects, rewrites headers, runs a chain of middleware and reshapes JSON in Ruby, and it shares a rate limiter, a response cache and its metrics between Ractors with no IPC, no Redis and no files.

Go is still 1.9× faster at plain proxying. On the JSON route Ruby beats Go's standard library and loses to a hand-written Go filter. What changed is that one Ruby process now does what used to take a pool of forks plus Redis: every Ractor sees the same counters, the same cache and the same limits, and they run in parallel.

The demo

An API gateway with six jobs

Everyone in the room knows what a gateway does, and each of these jobs either keeps Ruby busy or needs state that every worker can see.

  • Route by prefix to pools of upstream servers: /api to ports 9001 and 9002, /static and everything else to 9003 and 9004.
  • Balance by least outstanding requests, counted across every worker.
  • Rate limit per API key, with one count per key per second shared by every worker.
  • Cache /static responses for a second, in one cache shared by every worker.
  • Rewrite JSON: keep the fields the client asks for, camelCase every key, mask email addresses.
  • Report metrics for the whole process at /metrics, in Prometheus format.

All of it is plain Ruby objects. Requests and responses are Data values, every feature is a layer with call(request) { ... } in the spirit of Rack, and the layers are frozen. That makes the whole routes table shareable with one magic comment, rate-limit windows, cache entries and metric counters included, and every Ractor gets the same table. Only sockets and upstream pools belong to a single Ractor.

The Go twin has the same layers and the same semantics in 605 lines, shared through sync.Map and atomics, which is how Go has always worked. It ships in two builds: encoding/json, and a hand-written streaming filter on the experimental encoding/json/jsontext. The Ruby version is 376 lines.

The point of Ractors

Shared state without IPC

Forked workers share nothing they can change. A Puma cluster that wants one rate limit across workers needs Redis, metrics need a sidecar or memory-mapped files, and every worker keeps its own cache. Ractors live in one address space. Ruby lets them share frozen objects freely, and ratomic adds a few mutable structures that are safe to share: atomic counters, a concurrent map, a queue. So the gateway keeps its rate-limit windows, its cache and its metrics in one place, and all four Ractors update them in parallel.

Each check below ran against four workers. Ractors, threads and Go each share one copy of the state; forks get four copies that drift apart.

Forks fail all three in the expected way. Each scrape answers from whichever process caught the connection, so it reports a quarter of the traffic and a different number every time. Each process enforces the limit on its own, so 38,870 requests got through where 11,007 did with Ractors. Each process has its own cache, so the backend saw 38,729 requests instead of 10,000. Threads get the sharing right but share one GVL: in the four seconds of the metrics check they served 272,776 requests against 968,130 for Ractors.

Two details are worth knowing before you copy this. Ractors let 7 more than the limit through, where threads and Go hit 11,000 exactly. The rate limiter creates each second's counter with windows[key] ||= Counter.new, and when two Ractors race to create it, one counter overwrites the other and loses a count or two. Go's sync.Map#LoadOrStore has no such race, and ratomic's fetch_or_store would not either, but it runs its block while holding a lock, which is exactly the pattern that deadlocked Ruby 4.0.6 in log entry 10. So the gateway uses only the map's [], []= and delete, and I put it through 15 seconds of eight Ractors storing and replacing shared entries while 30 global collections ran, without a crash.

Ecosystemio-event+23%

Ten syscalls per request

On plain proxying Go led by 1.65×. A profile put three quarters of Ruby's time inside io-event's read and write calls, which is mostly the kernel, so I counted syscalls with strace.

# strace -c, one worker, raw route        Ruby: 45,167 requests   Go: 102,246 requests
  calls  syscall                          calls  syscall
 135510  write                           204492  write
 226139  fcntl                           205762  read
  90870  read                            102247  writev

io-event calls fcntl(F_GETFL) before every read and write to check the non-blocking flag. With an io_write hook installed, Ruby also writes each argument of IO#write(a, b) separately instead of with one writev. Both hooks are optional in the scheduler interface; without them, Ruby performs the non-blocking call itself and asks the scheduler only to wait.

Fix Async::Scheduler.undef_method(:io_read, :io_write). Four syscalls per request, one fewer than Go's first version. Pass-through rose 23% over async's defaults, and 9% over simply concatenating each response into one write.

08
RuntimeGC+45%

The Ractor tax was the garbage collector

Even with that fixed, a trimmed request cost 65 µs of CPU in a Ractor, 40 µs in the main thread and 42 µs in a forked process. Same code, same work. GC.stat inside a worker told the story.

GC runs in 5 s, main Ractor28440 major, 304 heap pages
GC runs in 5 s, worker Ractor12,371470 major, 13 heap pages

Koichi Sasada's commit abac51a1ce from 4 September gives every non-main Ractor the smallest heap that works, so that spawning 64 short-lived Ractors stays cheap. The main Ractor still starts with 2.5 MB. A server Ractor allocates hundreds of objects per request but keeps few of them, so its heap never looks crowded enough to grow, and it collected every eight requests.

Fix RUBY_GC_RACTOR_HEAP_INIT_BYTES=2621440, the same 2.5 MB the main Ractor gets, set by bin/proxy. GCs per Ractor fell from 38,256 to 367 and the JSON route rose 45%. It is read at boot only; GC.config cannot change it at runtime.

09
RuntimeJIT

The JIT barely moves the needle

Against the interpreter, YJIT adds 3% on pass-through and 5% on the JSON route; ZJIT adds 7% and 3%. The time goes to syscalls, the regex engine, the json extension and the GC, all of them C. ZJIT, which is still experimental, ran inside Ractors without complaint and edged out YJIT on pass-through.

Ruby 4.0.6: more Ractors, less speed, then silence

On the latest release, the same proxy served fewer pass-through requests with four Ractors than with one: 58,000 against 79,000. On the JSON route it stopped dead within seconds. Zero CPU, every thread parked in a futex wait, listen queues filling up. gdb, which had to start Ruby itself because this machine forbids attaching to a running process, showed the cycle.

#20 ratomic::init::anon () from ratomic.so

Map#increment computes the new value by calling back into Ruby while it holds a shard lock. On its way out of that call, thread 5 stops at the GC barrier. Thread 4 started the GC and now needs the same lock to mark the Map. On master each Ractor collects its own heap without stopping the others, and the cycle never formed under the same load. Master still runs an occasional global GC, which could close it.

Fix One Ratomic::Counter per Ractor instead of a Map: pure atomics, no lock, no callback. The deadlock went away and so did the negative scaling: four Ractors on 4.0.6 now serve 216k pass-through and 60.1k trimmed requests per second, against 367k and 95.8k on master.

11
Harness

Tooling paper cuts

  • perf_event_paranoid is 4 and there is no sudo, so no perf. I profiled with stackprof in thread mode, where all the work runs in the main Ractor.
  • ptrace_scope is 1, so strace and gdb only see processes they start themselves.
  • wrk2's bundled LuaJIT writes a bytecode object that modern binutils call corrupt, and the binary panics on start. I rebuilt it against Homebrew's LuaJIT 2.1, with the bytecode compiled as C source and the removed luaL_reg name aliased back.
  • pkill -f 'gdb -batch' matched my own shell's command line and killed it. So did a pkill -f proxy_nohooks earlier. Exact process names only, from then on.
  • Go listens on [::]:8080, which shows up only in /proc/net/tcp6, so the harness waited forever for a listener it could not see.
  • Forked Ruby workers hold port 8080 for a moment after the parent dies, so the harness now waits for the port to clear between runs.
  • Go gains little from a second CPU: 204k requests per second on two against 144k on one, on either pair of cores. Its scheduler hands goroutines stuck in syscalls to extra OS threads, and those need CPU too. The same GOMAXPROCS=2 with four CPUs available reaches 274k.
12
GoFairness

My buffers flattered Go's syscalls and inflated its memory

At 10,000 connections the first run had Go at 700 MB against Ruby's 424 MB. Most of that was my doing: every Go connection had a 16 KB read buffer, twice the 8 KB Ruby gives each IO. The bigger buffer also let Go read a whole 12 KB upstream response in one syscall where Ruby needs two.

Fix 8 KB buffers on both legs, matching Ruby's IO_RBUF_CAPA_MIN, and every Go measurement re-run. Go's memory at 10,000 connections fell to 421 MB. The jsontext build went from 99.6k to 91.9k on the JSON route, because it now needs a second read per response just as Ruby does. Pass-through went from 510k to 508k.

13
Feedback

The first version was too kind to Ruby

The verdict on version one was blunt: too terse to be elegant, too simple, and suspiciously good for Ruby because the work happened outside it. The profile agreed. Gateway code was 3.6% of a pass-through request and 2.2% of a JSON one; sockets and the kernel took 70%, and the json extension took 45% of the JSON route.

Rebuilt as a gateway that parses HTTP into objects, rewrites headers, chains layers and reshapes JSON in Ruby. On four Ractors, pass-through went from 356k to 228k requests per second, and the JSON route, now doing far more work, from 94.1k to 34.6k. That is what it costs to make Ruby do the work.

14
RactorsDesign

Frozen objects are the sharing model

Ruby lets Ractors share frozen objects and nothing else, so the design starts there. Every layer is a frozen object, usually a Data value, whose only mutable parts are ratomic structures. A frozen object with shareable instance variables can be called from any Ractor, and classes the main Ractor defined are readable everywhere, so the layers need no special handling at all.

RateLimit = Data.define(:per_second, :plans, :windows) do
  def initialize(per_second:, plans: {}, windows: Ratomic::Map.new) = super
  ...
end

ROUTES = Gateway.routes do ... end    # shareable_constant_value: experimental_everything
Ractor.shareable?(ROUTES)             # => true, windows and counters included

GCratomicHeld up

Objects made in one Ractor, read by all

The cache stores responses built inside a worker Ractor, and the rate limiter creates its counters there, all kept in a map that belongs to the main Ractor. With master's per-Ractor collector, that could become a use-after-free if a worker's GC reclaimed an object only the map still pointed at. Making each value shareable before storing it is what keeps it alive, and I tested that before building on it: eight Ractors hammering one map for 15 seconds while the main Ractor forced a global collection every half second.

Shared state

Forks get it wrong, quietly

Nothing crashes in fork mode. The same code just gives different answers: 38,870 requests through a limit that let 11,007 through with Ractors, 38,729 backend fetches where Ractors needed 10,000, and a /metrics page that changes from one scrape to the next. That is the failure mode that sends teams to Redis. The shared state section has the full comparison.

17
JIT

The JIT still barely moves the needle

Even the rewrite, the most Ruby-heavy code in the gateway, gains only about 5% from a JIT: 87.6 µs per document on the interpreter, 83.1 µs with YJIT and 84.9 µs with ZJIT. Idiomatic Ruby spends its time inside core methods like split, to_h and join. They are written in C, and no JIT makes them faster.

18
Harness

More paper cuts

  • My upstream ignored Connection: close, so the harness waited forever for it to hang up after a /__count request.
  • Ruby's TCPServer.new does not set SO_REUSEADDR. After eight /metrics scrapes closed by the server, the harness's port check failed for 60 seconds on the leftover TIME_WAIT sockets. The gateway itself rebinds through SO_REUSEPORT, and now sets both.
  • Go's listener does not set SO_REUSEPORT, so its TIME_WAIT sockets blocked the first version's listener, which set only that.
  • The upstream's request counter covers the whole process, and I summed two of its ports. Every fetch counted twice and looked like a cache bug until a timeline of x-cache headers showed exactly one miss per second.
  • pkill -f 'gateway.rb' killed my own shell. Third time today.
  • gateway-jsontext is 16 characters, and pkill -x matches at most 15.
  • At full load, cache stampedes add misses in every mode, so the cache check runs at a steady 40,000 requests per second with wrk2.
  • Ten seconds of the rate-limit check touch eleven clock seconds, and a correct limiter only lets 11,000 through when neither partial second is shorter than a fifth of a second. A later run started just before a second boundary and threads allowed 10,446, so the harness now starts that check mid-second.
19
RuntimeGC−70% memory

Frozen garbage that no collector frees

Looking for a workload where forks lose on a number and not only on correctness, I gave the cache 64 KB responses. Forks should need four copies of it and Ractors one. Instead four Ractors used as much memory as four forks, while four threads, which share one cache too, used a quarter of it.

Inside a worker Ractor, plain strings, frozen strings and large strings were all collected. Objects that went through Ractor.make_shareable, or through Ractor.shareable?, which sets the same flag, were not, and memory grew at exactly the rate they were made.

Ractor.new { loop { Ractor.make_shareable("x" * 65_536); sleep 0.001 } }
loop { sleep 1; puts File.read("/proc/self/status")[/VmRSS.*/] }
$ ruby repro.rb
VmRSS:	    76944 kB
VmRSS:	   136880 kB
VmRSS:	   196736 kB
VmRSS:	   256724 kB
VmRSS:	   316784 kB
# after 30 s: 1.7 GB, GC.stat(:global_gc_count) = 0

The per-Ractor GC pull request, ruby/ruby#18194, explains it. A Ractor's own collection pins every shareable object, since another Ractor might hold it: “Only a global GC can decide a shareable object is dead.” A global GC runs on an explicit GC.start, when the number of shareable objects grows, or to reclaim the pages of dead Ractors. Bytes are not on that list, so a few thousand large frozen responses never set one off.

Fix The main Ractor forces a global collection once a second, Thread.new { loop { sleep 1; GC.start } }. Four Ractors then peak at 207 MB instead of 698 MB, and p99 goes from 1.52 to 2.74 ms, because a global collection pauses every Ractor. The real fix belongs in Ruby: the trigger should count bytes, not only objects.

The timer has a side effect I did not expect. Before I took it out of the stock build, stock master already reached 32.4k on the API route, against 34.1k with the heap variable as well: a global collection every second also grows the worker Ractors' heaps, which hides the wall from entry 08. The ladder above measures every fix without the timer.

The numbers

Scaling across cores

Everything ran on one machine over loopback, each role pinned to its own cores so the load generator and the upstream never compete with the gateway. Each point is the median of three 8-second wrk runs with 256 keep-alive connections after a 2-second warm-up. CPU time comes from /proc; memory is PSS, so forked processes are not double-counted.

Ractors and forks track each other on every route, so sharing the cache and the counters costs Ractors nothing measurable. Threads stay flat behind the GVL. Go leads pass-through by 1.9× and cache hits by 1.6×. On the API route Ruby beats Go's standard library and trails the jsontext build: one CPU gives 8.6k against 20.1k, four give 34.6k against 62.1k. Ractors keep their cores busier than Go does, 3.96 of four on the API route against 3.5 for Go, which narrows but does not close the gap.

What each fix bought

The two fixes from the first round still matter. On four Ractors, the 2.5 MB Ractor heap takes the API route from 17.0k to 34.0k requests per second, and removing async's IO hooks takes pass-through from 202k to 234k. The GC timer from entry 19 is about memory, and on throughput it moves pass-through from 234k to 235k. The JIT adds the least. Against Ruby 4.0.6 the gap is the widest of all: the same code with four Ractors serves 9.7k API requests per second there and 34.7k on master.

Ten thousand connections

This is the Fiber half. Every request waits 50 ms at the upstream, so a connection can complete at most 20 requests per second; the grey line is that ceiling, and a thread pool of 16 would top out at 320. At 10,000 connections four Ractors served 88.6k requests per second with a p99 of 195 ms, against Go's 178k. A single Ractor on one core saturates first.

Latency at a fixed rate

wrk measures latency while pushing as hard as it can, which hides queueing. wrk2 holds a constant rate and corrects for that, so these percentiles are what a client sees at a steady load. Four workers each, 30-second runs. At 150,000 pass-through requests per second Ruby's p99 is 27 ms against Go's 2.3 ms; on the API route at 20,000 it is 7.9 ms against 1.7 ms for the jsontext build.

Memory

Ractors share one heap of code and frozen data; forks share only what copy-on-write has not copied yet, and Ruby's GC keeps writing to its pages. PSS splits shared pages fairly, so the fork numbers are not inflated. An idle keep-alive connection costs Ruby about 27 KB as a parked fiber and Go about 13 KB as a parked goroutine. Under the API load, four Ractors peak at 114 MB, four forks at 141 MB and Go at 37 MB.

A cache makes the difference plain. Serving 1,000 cached responses of 64 KB, four Ractors peak at 207 MB and four forks at 681 MB, because every fork fills a copy of its own; with eight workers it is 255 MB against 1262 MB. The Ractor numbers need the fix from entry 19: without it, four Ractors reach 698 MB in the same ten seconds and keep growing.

The rewrite, in isolation

The API route's CPU stage on its own: parse the 12,280-byte document, keep four fields of each of its 32 objects or keep them all, camelCase every key, mask the emails, serialize. One core, the gateway's own code in both languages. Ruby beats Go's standard library on the filtered document and loses on the whole one, where its per-key work dominates. The jsontext build never builds a map at all and wins both. The library chart below is the parse-and-generate part alone, from the first round.

The cool and the ugly

Cool

  • Shared state with no IPC. One rate limit, one cache and one set of metrics for four Ractors running in parallel, where forks need Redis, a sidecar or memory-mapped files.
  • Sharing costs nothing measurable: Ractors match forks request for request on every route.
  • One copy of everything: with a 64 MB cache, four Ractors peak at 207 MB and four forks at 681 MB.
  • async, io-event and ratomic run inside Ractors on master without changes.
  • The design falls out of Ruby's rules. Frozen Data layers are shareable, so a 20-line DSL builds a routes table every Ractor can use.
  • The same file runs as Ractors, threads or forks, which makes the comparisons above a one-word change.

Ugly

  • Go is still 1.9× faster at pass-through and 1.6× at cache hits, and idiomatic Ruby spends its time in core methods that no JIT speeds up.
  • Warning[:experimental] = false, a boot-time environment variable for the Ractor heap, and a monkey patch on async's scheduler. Each is worth double digits.
  • ratomic needs a patched Rust binding on master. Only part of its Map is safe to use: the methods that take a block hold a lock while they run your code.
  • Without a race-free create-if-missing, the shared rate limiter lets a couple of extra requests through per window.
  • Large frozen objects are freed only by a global collection, which nothing triggers for them, so the gateway forces one every second and pays for it in p99.
  • SO_REUSEPORT pins a connection to one Ractor for life, and class ownership means any gem that memoizes into class-level state breaks inside a worker Ractor.
  • No profiler I tried looks inside a worker Ractor; every profile here ran in thread mode.

What a few more years might buy

Every wall in this log was a default or a library that has not caught up with a runtime that changed this year.

  • Server-shaped GC defaults: a Ractor heap that grows with allocation rate as well as live data.
  • Shareable containers with the full set of atomic operations: compare-and-set, and a create-if-missing that never runs user code under a lock.
  • An event loop that remembers each descriptor is non-blocking instead of asking the kernel on every read.
  • Gems written for ownership: no class-level caches, so they load in any Ractor.
  • Profilers that see every Ractor.
  • Then Rails: fibers first, Ractor workers instead of forks for memory and shared caches, and parallel work inside one request.

So, are we fast yet? Not at raw speed. Once Ruby does the work, Go does it faster on this machine, and a JIT will not close that gap while the work sits in core methods. But the question has changed. For the first time one Ruby process can use every core and share live state between them, the thing we reach for Redis, sidecars and memory-mapped files to fake today. That part is here.
